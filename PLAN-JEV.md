# PLAN-JEV — Дешёвый семантический слой (TypeSafe Jev и аналоги)

> Контекст: Jev (TypeSafe AI, сентябрь 2026) — первая «System One» модель:
> не генерирует текст, возвращает калиброванные распределения вероятностей
> над вариантами (Choice / Noul / Score). Дёшево ($0.042/1M input), быстро
> (десятки мс), все вопросы одного запроса независимы и параллельны.
> Разбор — [habr.com/ru/articles/1085450](https://habr.com/ru/articles/1085450/).
>
> Принципиальная позиция: наш ядро — многошаговый агент (Claude Code CLI +
> sstats MCP). Jev его НЕ заменяет и не встраивается в агента. Это отдельный
> дешёвый слой ВОКРУГ агента, который включается по экономике масштаба.

---

## Почему сейчас НЕ время (триггеры запуска)

Сегодня (1 пользователь, локально) стоимость решений не узкое место — узкое
место сбор данных и reasoning. Слой включаем, когда выполнится хотя бы одно:

- **T1. Аудитория**: 20+ активных пользователей в день;
- **T2. Стоимость**: > $5/день на модельные вызовы агента;
- **T3. Очередь**: пользователи ждут разбор > 3 минут из-за загрузки VPS;
- **T4. Продуктовая потребность**: хотим «кандидатов в value» по всем матчам
  дня до запросов пользователей (ночной скрининг).

До триггеров этот план не трогаем — он не блокирует фазы C–G и этап 5.

## Этап J0 — Кэш разборов (без Jev, обязательный первый шаг)

Максимальный выигрыш при масштабе даёт не ИИ-слой, а архитектура:
100 пользователей разбирают в основном одни и те же топ-матчи.

- Ключ кэша: `gameId + тип разбора + свежесть данных` (форма/кэфы меняются —
  TTL 3–6 ч для доматчевых, инвалидиция при смене кэфов > 2%);
- Хранилище: `data/analysis-cache.json` (или sqlite при росте);
- Роут на сервере: перед запуском агента проверяем кэш, отдаём готовое;
  заголовок в чате «готовый разбор от HH:MM · данные на HH:MM» + кнопка
  «пересчитать свежим прогоном»;
- Метрика: hit-rate кэша; цель на старте — 50%+ типовых запросов.
- **Критерий:** повторный запрос того же матча не поднимает агент.

## Этап J1 — Абстракция решателя + маршрутизация запросов

Вводим интерфейс «дешёвого решателя» в сервере, чтобы не привязываться к Jev
(сервису нет и месяца; категория породит конкурентов — подключаем класс, не вендора).

- `server/semantic.js`: `choice(state, options, criteria)`, `noul(state, statement)`,
  `score(state, object, scale)`; провайдер за env (пока — заглушка, Jev —
  при доступности API и ключа в `data/jev-key.json`);
- Первая задача — маршрутизация: «какой матч имеет в виду пользователь?»
  (Choice по матчам дня из /api/sstats/*), «какой пресет подходит под вопрос?»;
- Включается ДО агента: экономит запуск целиком, когда вопрос сводится
  к кэшированному разбору;
- **Критерий:** «разбери дерби в воскресенье» находит матч без агентного прогона.

## Этап J2 — Каскад: дешёвый слой перед агентом

Схема System 1 → System 2 на каждом пользовательском запросе:

```
запрос → J1-маршрутизация → кэш (J0)?
   ├─ да  → готовый ответ (центы → ноль)
   └─ нет → быстрые проверки → шаблонный короткий ответ?
             └─ нет → полный агент (дорого)
```

- Быстрые проверки: Noul-вопросы по state матча и вопросу
  («хватит ли имеющихся данных?», «запрос про конкретный рынок или общий?»);
- Порог уверенности настраивается; всё, что ниже — агенту;
- Метрики: доля запросов, закрытых без агента; расхождение коротких ответов
  с агентными (контроль качества на сэмпле);
- **Критерий:** 30%+ запросов закрыто без агента без падения качества.

## Этап J3 — Ночной предскрининг «кандидатов в value»

Продуктовая фишка: до прихода пользователей страница событий уже знает,
где искать value.

- По расписанию (cron) прогоняем все матчи дня: state = форма, xG, кэфы
  8 букмекеров, H2H; вопросы — Score/Noul по отклонениям
  («лучшая цена выше консенсус-fair на 3%+ при подтверждаемой форме?»,
  «событие похоже на исторические апсеты этой лиги?»);
- Результат: бейдж «кандидат» на карточках + отдельная плитка-фильтр;
  полные разборы по кандидату — по кнопке (и в кэш J0);
- Стоимость: ~1000 матчей × десятки вопросов = центы за ночь;
- **Критерий:** кандидаты за 30 дней дают value-статистику лучше случайной
  выборки (проверяем по трекеру сигналов).

## Этап J4 — Верификация ответов агента

Страховка достоверности при масштабе (цена ошибки = доверие к «Точности»).

- После каждого полного разбора — пакет Noul-проверок по state собранных
  данных: «каждая цифра в таблицах подтверждается данными инструмента?»,
  «вердикт не противоречит собственным вероятностям?»;
- Провал проверки → пометка «требует проверки» в чате + не пускать
  в автосигналы без подтверждения;
- **Критерий:** на исторических разборах ловит подмену цифр
  (сэмплируем 20 старых, мерим precision).

## Этап J5 — Калибровка на наших данных (сквозной контроль)

- Датасет: трекер сигналов (исходы won/lost) + вердикты каскада J2;
- Ежемесячно: reliability-диаграмма «сказано 0.7 → зашло в X%»;
  расхождение > 10 п.п. → понижаем порог каскада или меняем провайдера;
- Отдельно: A/B «слоя нет / слой есть» по cost и удовлетворённости.

## Риски и ограничения (фиксируем, чтобы не наступать)

- Jev: single-hop, неустойчива к сконструированному тексту, нет независимых
  бенчмарков, сервису нет месяца → только за абстракцией (J1), не в ядро;
- Вопросы одного запроса независимы — зависимости выражаем в КОДЕ (наш случай:
  сначала арифметика fair/value, семантика — только на качественных факторах);
- Чисто числовые вещи (fair odds, маржа, value) считаем кодом — Jev для этого
  не нужен и не должен;
- Русский рынок: доступность API/оплата неясны — проверять до J1.

## Порядок

J0 → (триггер T1–T4) → J1 → J2 → J3 → J4; J5 — постоянно после J2.
J0 можно делать в любой момент после этапа 5, он полезен даже без Jev.
